01요구사항 및 기능

목적·사용자

운영/개발 담당자가 개선요청을 상태별로 조회하고, 항목을 열어 상세·스크린샷을 확인한 뒤 처리 시작/완료를 수행한다.

검색

설명 또는 pageUrl keyword, 등록일 from/to, ALL/PENDING/IN_PROGRESS/DONE tab, 20건 페이지네이션을 지원한다.

현재 status weakness

중요프론트는 PENDING→IN_PROGRESS→DONE 버튼만 노출하지만 backend updateStatus는 enum 값이면 어떤 방향도 저장한다. API가 역전이/건너뛰기를 막지 않는다.

02API 인터페이스

controller는 req.user에서 organizationId/user metadata를 추출하며 조직 정보가 없으면 BadRequest. 명시적인 JwtAuthGuard decorator는 현재 파일에 보이지 않는다.

03DB·검증·수락 기준
영역현재 확인수락 기준
DB/성능목록은 screenshot CLOB를 select하지 않고 detail에서만 읽는다. ORGANIZATION_ID/STATUS index가 있다.list response에 screenshot이 없고, detail에서만 전체 이미지가 로드된다.
필드 validationpageUrl 500, elementText 1000, tag 100, description 2000, status enum; from/to/page/limit query.길이/enum 오류는 저장하지 않고, keyword는 desc/pageUrl만 검색한다.
tenantservice findOne/findAll/updateStatus where에 organizationId 포함.다른 조직 imprId detail/status 변경 불가; body의 requester/org를 신뢰하지 않는다.
transitionUI는 다음 상태만 노출하지만 service는 현재 상태/actor/이력 검증 없이 enum을 직접 대입한다.현재 baseline 테스트는 direct/reverse PATCH 가능성을 residual risk로 기록한다. 인접 상태 guard·audit은 후속 승인 없이는 설계에 추가하지 않는다.
오류list catch는 empty, detail catch는 toast+close, status catch는 toast.오류 후 modal/loading이 정리되고, empty와 조회 실패 구분 문제를 별도 개선으로 남긴다.
상태 수락DONE은 frontend에서 button이 사라진다.UI baseline은 DONE terminal처럼 보이지만 API contract가 실제로 terminal인지 별도 backend decision으로 확인한다.
