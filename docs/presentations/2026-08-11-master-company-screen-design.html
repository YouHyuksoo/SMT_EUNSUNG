01요구사항과 사용자

목적

확인ISYS_ORGANIZATION 기반 회사 목록을 검색·추가·수정·삭제한다. 수정 모드에서는 회사에 속한 PLANTS 사업장과 EUNSUNG / 2F / PROD2 CELL을 관리한다.

공장 계층의 기준은 회사 API가 아니라 별도 /master/plants API에 있다.

사용자·권한

추정업무 마스터 관리자 또는 조직 관리자. 화면 소스에는 역할명이 직접 선언되지 않고, 인증 컨텍스트는 @Company()·@Plant()와 전역 인증 전제에 의존한다.

확인로그인용 활성 회사/사업장 공개 조회 API가 별도로 존재한다.

핵심 결과

회사 행을 선택하면 기본정보·연락처를 편집할 수 있다.

수정 시 사업장 추가/삭제와 CELL 명칭·사용·정렬순서 변경을 별도 저장한다.

03업무 규칙·범위 경계
구분확인된 규칙화면 처리·주의
회사 키·필수companyCode 신규 필수·최대 50자, companyName 필수·최대 200자. 수정 시 회사코드는 입력 비활성.행 식별자는 companyCode::plant; plant는 view에서 organizationId 문자열로 내려온다.
기본정보bizNo, ceoName, address, tel, fax, email, remark는 선택 입력이며 DTO 길이 제한을 따른다.빈 선택값은 회사 저장 payload에서 undefined로 정리한다. remark는 실제로 organization full name에 매핑된다.
사업장수정 패널에서 plantType=PLANT을 조회하고 회사코드로 클라이언트 필터링한다. 사업장 추가는 코드·명칭 필수, 삭제는 복합경로 확인 후 실행.사업장 추가/삭제는 회사 저장과 분리된 API 요청이다. 목록 조회 실패와 0건 표현을 구분할 것.
CELLplantType=CELL 중 plantCode=EUNSUNG, shopCode=2F, lineCode=PROD2만 표시한다. 수정 가능 속성은 plantName/useYn/sortOrder.명칭 필수, 정렬순서는 0 이상의 정수. 코드 4개는 읽기 전용이며, CELL은 별도 추가/삭제 UI가 없다.
변경 보호회사 폼 또는 CELL draft가 dirty이면 패널·행 전환 전에 useUnsavedGuard 확인을 연다.저장 중 버튼·닫기 정책을 유지하고, CELL 저장 실패 시 초안과 선택 컨텍스트를 보존한다.

04수락 기준
  • 회사 검색·추가·수정·삭제 후 grid가 실제 응답으로 갱신된다.
  • 수정 패널에서 사업장 조회·추가·삭제가 회사 키와 테넌트에 맞는다.
  • PROD2 CELL만 노출되고 명칭/사용/정렬 검증·재시도가 동작한다.
  • dirty 상태에서 행 전환·닫기 시 입력 유실을 막는다.
  • 오류와 빈 목록을 다른 상태로 표시하고 저장 실패 시 값을 지킨다.
  • 인증·tenant 경계(@Company/@Plant 대 @OrganizationId)를 coordinator가 승인한다.

명시해야 할 mismatch

구현 불일치회사 화면은 회사 view와 PLANTS 계층을 한 패널에서 묶지만 백엔드는 tenant decorator가 다르다.

구현 불일치회사 삭제는 실제 hard delete이고, company controller에는 PlantController처럼 로컬 @UseGuards(JwtAuthGuard)가 보이지 않는다.

구현 불일치CellManagementSection은 선택 회사가 아니라 고정 EUNSUNG/2F/PROD2 조건을 사용한다. 실제 운영 회사가 다르면 화면 정의를 바꾸지 말고 계약을 먼저 확인한다.
