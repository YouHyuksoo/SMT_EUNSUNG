01요구사항 및 기능

목적·흐름

목록을 검색/필터/export하고, 신규/선택 행을 우측 슬라이드 패널에서 저장한다. 행 삭제는 위험 확인 modal을 거친다.

권한·키

프론트 역할은 ADMIN/MANAGER/OPERATOR/VIEWER이고, 백엔드는 USER_LEVEL을 역할로 변환한다. UI의 email이 API 식별자다.

현재 persistence 주의

불일치ISYS_USERS에는 role/status/photo/pdaRole/empNo 전용 컬럼이 없고, service view가 일부 값을 파생하거나 고정한다. 폼이 보여도 그대로 저장된다고 가정하지 않는다.

03비즈니스·구현 규칙

필수·불변생성 email/user ID와 password가 DTO 필수. 수정 시 email은 disabled. 신규 폼은 password가 비면 admin123을 보낸다.신규 저장 버튼은 email이 없으면 disabled; 서버는 password 최소 4자를 검증한다.
역할ADMIN→9, MANAGER→5, OPERATOR/VIEWER→1. VIEWER는 서비스에서 operator 수준으로 매핑되는 현재 계약이다.role select와 배지를 표시하되 실제 권한은 서버 level 변환을 따른다.

현장 부서/PDA부서는 DepartmentSelect, PDA 역할은 GET /system/pda-roles/active다.PDA 조회 실패는 빈 option으로 조용히 대체한다.

03DB·검증·수락 기준
영역현재 확인수락 기준
조직 경계controller/service가 @OrganizationId()와 organizationId로 조회/변경 조건을 붙인다.다른 조직의 user ID를 조회·수정·삭제할 수 없어야 한다. controller에 명시 guard가 보이지 않으므로 적용 경계를 별도 확인한다.
DTO validationemail/password/role/status 값은 class-validator로 검증; empNo/photoUrl/pdaRoleCode는 DTO에 있지만 서비스 view/저장과 어긋난다.현재 계약을 테스트할 때 표시값과 실제 Oracle 컬럼의 차이를 증거로 남긴다.
사진파일은 디스크에 저장 시도하지만 service는 DB URL update를 skip한다.현재 baseline에서는 성공 toast와 재조회 후 null photo가 가능한 상태를 명시한다. persistence 보완은 별도 계약이다.
삭제프론트 confirm 후 DELETE; backend는 hard repository.delete.soft/hard semantics를 문서 밖에서 확정하기 전 “소프트 삭제”라고 표기하지 않는다.
오류list/delete/PDA load는 catch ignore 또는 []로 삼킨다.현 화면이 멈추지 않고 재조회 가능하되, 조회 실패와 빈 목록을 구분하는 개선은 후속 acceptance로 둔다.
