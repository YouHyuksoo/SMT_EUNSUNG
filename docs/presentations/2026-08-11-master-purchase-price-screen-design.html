01요구사항 및 사용자

목적

기준일에 유효한 구매단가를 품목·공급사·구입유형으로 확인하고 적용기간·통화·세율·변경사유를 관리한다.

기본 조회는 오늘 기준 유효단가만 표시한다.

식별자·권한

자연키는 dateset + itemCode + supplierCode + lineType + organizationId. 인증 조직 범위를 서버가 결정한다.

수정 시 key select는 disabled, originalDateset을 전송.

저장 영향

저장 전 impact API로 기존 기간과 입고 영향 건수/금액을 확인하고 확인 모달에서 실제 저장한다.

수정 시 승인여부·승인번호·승인자·승인일은 읽기 전용.

03DB·검증·완료 기준

DB / 서버 불변식

  • IM_ITEM_UNIT_PRICE PK는 dateset/item/supplier/lineType/organization. 목록은 ID_ITEM·ICOM_SUPPLIER를 left join한다.
  • DTO는 적용기간 날짜, 금액/세율 0 이상, code length를 검증하며 Oracle 원문 오류를 BadRequest message로 보존한다.
  • impact는 IM_ITEM_RECEIPT에서 dateset 이후 입고 건수·금액을 계산한다.
  • approvalNo/priceChangeConfirmYn/confirmBy/confirmDate는 조회·read-only 정보이며 이 controller에는 승인 mutation이 없다.

수락 시나리오

  • 기준일·유효단가 checkbox·품목·공급사·유형 필터가 SQL 조건과 일치한다.
  • 신규/수정 전 impact를 확인하고, 사용자가 취소하면 POST/PUT을 호출하지 않는다.
  • 수정 시 key 선택값을 바꾸지 않고 originalDateset으로 정확한 row를 갱신한다.
  • 0 이상 numeric 값, 날짜/필수 누락, 중복/Oracle 오류가 화면에 유지된다.
  • 저장 성공 후 panel close와 목록 재조회, 승인 정보 read-only 표시가 동작한다.
04현재 구현 불일치 및 백엔드 전용 동작

불일치impact와 실제 service 경계

  • getImpact(create)는 기존 closingRows와 입고 영향액을 읽어 “기존 단가가 마감된다”고 안내하지만, 관찰된 PurchasePriceService.create()는 명시적으로 기존 row의 DATEEND를 update하지 않고 새 row를 save한다.
  • 실제 마감이 DB trigger/외부 처리인지 현재 source만으로 확정할 수 없다. 설계는 메시지를 유지하되 운영 DB에서 pre/post 검증이 필요한 mismatch로 표시한다.
  • controller에는 삭제 endpoint가 없고, UI도 삭제를 제공하지 않는다.

백엔드 전용현재 UI에 없는 action/field

  • approval mutation/반려 API가 없으며 승인 컬럼은 조회 전용이다.
  • validOnly=N 전체이력 query, supplier search/limit API, audit/tenant 처리.
  • service의 toOracleException()이 driverError 원문을 보존하는 오류 경로.
  • list 응답의 lastModifyBy/lastModifyDate는 현재 grid/form에 모두 노출되지 않는다.
