03DB·검증·완료 기준

DB / 서버 불변식

  • 엔티티는 IM_ITEM_MASTER에 supplier/item/dateset/org 복합 PK를 사용한다.
  • create는 findOneBy key 후 save. update는 originalDateset key로 update하고 새 dateset로 재조회.
  • DTO는 code 길이, orderRate/수량/비율/ESD 0 이상, paymentType 필수 등을 검증한다.
  • 목록 query는 UPPER 검색과 OFFSET/FETCH를 사용하고 tenant bind를 포함한다.

수락 시나리오

  • 검색·supplier·orderType 필터가 목록과 total에 반영된다.
  • 신규에서 품목/공급처/기간/지불유형 누락은 저장되지 않는다.
  • 수정 시 dateset만 바꿔도 originalDateset 기준 row가 갱신되고 새 날짜로 반환된다.
  • 중복 create와 없는 update/delete는 오류가 되고 목록/폼이 임의로 성공 상태가 되지 않는다.
  • 코드 필드는 badge/label로 표시하고 audit 값은 사용자 입력으로 노출하지 않는다.
04현재 구현 불일치 및 백엔드 전용 동작

불일치현재 UI의 한계

  • controller에는 DELETE가 있지만 itemSupplierColumns와 form/page에는 삭제 icon·확인 modal이 없다.
  • backend query DTO의 inspectRule 필터는 page toolbar에 노출되지 않는다.
  • useUnsavedGuard가 page/form에 연결되지 않아 패널 작성 중 행 전환 시 dirty confirmation이 없다.
  • 서비스에는 dateset/dateend 순서 또는 기간 겹침을 별도로 검사하는 로직이 관찰되지 않는다. DB/업무 기준 확인 전 UI 동작을 추정하지 않는다.

백엔드 전용화면에 없는 규칙·action

  • DELETE route와 NotFound 처리.
  • inspectRule 정확 필터 및 raw SQL total count.
  • ENTER/LAST_MODIFY 사용자·일시 기록과 organizationId 격리.
  • supplier/item display 이름을 ID_ITEM·ICOM_SUPPLIER에서 join하는 데이터 enrichment.
