01요구사항과 사용자

목적

확인창고 코드·명·유형·공장·라인·공정·기본창고를 관리하고, 두 번째 탭에서 창고별 zone/row/col/level 로케이션을 관리한다.

UI와 field help는 WAREHOUSES 계열 명칭을 사용하지만 entity는 ICOM_WAREHOUSE다.

사용자·권한

추정재고/자재 기준정보 관리자. 화면 역할명은 없고 warehouse 및 location API는 @OrganizationId()를 사용한다.

핵심 결과

창고/로케이션 탭 전환 시 header action이 새로고침·등록으로 교체된다.

창고 유형은 서버 필터, 검색은 현재 client filter; 로케이션은 창고 선택 filter를 먼저 조회한다.

04수락 기준
  • 탭 전환 때 header action과 목록 컨텍스트가 교체된다.
  • 창고 유형·FLOOR 조건·기본창고 boolean이 API/DB와 일치한다.
  • 로케이션 parent filter, composite key edit/delete, coordinate fields가 동작한다.
  • 중복/재고 Conflict/API 오류와 진짜 empty를 다른 상태로 표시한다.
  • 저장 성공 후 해당 탭/필터를 유지한 채 재조회한다.
  • ICOM_*와 legacy WAREHOUSES SQL을 실제 Oracle schema에 대조한 뒤 완료한다.

명시해야 할 mismatch

구현 불일치entity/controller는 ICOM_WAREHOUSE 계열인데 frontend SQL/help는 WAREHOUSES, COMPANY='40', PLANT_CD='1000'을 제시한다.

구현 불일치entity의 isDefault는 string인데 frontend WarehouseData는 boolean이고 grid의 truthy check가 “N”도 체크로 오인할 수 있다.

구현 불일치주석의 soft delete와 실제 hard delete가 다르며 location delete에는 재고 참조 검사도 없다.
