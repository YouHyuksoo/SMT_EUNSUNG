01요구사항과 사용자

목적

확인고객코드·한글/영문명·사업자·거래상태·지불·신용·연락처·유효기간을 조회·등록·수정한다. 목록 표시는 코드값이 아니라 ComCodeBadge 명칭을 우선한다.

기준 테이블은 조직 ID와 함께 복합키를 가진다.

사용자·권한

추정영업/수주 또는 기준정보 관리자. 실제 권한 역할명은 화면 소스에 없으며, 백엔드 JwtAuthGuard와 @OrganizationId()가 인증·조직 범위를 결정한다.

핵심 결과

상태 필터와 검색으로 고객을 찾고, 등록/행 선택으로 상세 패널을 연다.

필수 입력 검증 후 POST/PUT 성공 시 목록을 다시 읽는다.

03업무 규칙·범위 경계
구분확인된 규칙화면 처리·주의
필수 입력UI 검증은 customerCode, customerName, customerNameEng, address, telNo가 비어 있지 않은지 본다.백엔드 DTO는 여기에 더해 businessStatus, businessType, paymentType, creditGrade, dateset, dateend도 필수다.
기본값신규 form 기본값은 상태 A, 유형 C, 지불 D, 신용 A, 시작일 오늘, 종료일 9999-12-31, 금액 0이다.코드 필드는 BUSINESS_STATUS/BUSINESS_TYPE/PAYMENT_TYPE/CREDIT_GRADE 공통코드 선택을 사용한다.
검색·필터프론트는 limit=500, search, businessStatus를 전송한다. 서비스는 고객코드/한글명/영문명 LIKE를 조직 범위에서 실행한다.DTO에는 paymentType query도 있지만 현재 UI에는 결제조건 필터가 없다.
자연키CUSTOMER_CODE + ORGANIZATION_ID가 PK다. 수정 URL은 customerCode로 식별한다.구현 불일치현재 압축된 CustomerFormPanel의 코드 입력 비활성 여부를 계약으로 확정해야 한다. service는 update payload의 customerCode를 저장하지 않는다.
코드 라벨원시 코드 대신 공통코드 배지를 렌더링한다.실 DB 코드 그룹/번역이 없으면 코드와 fallback 라벨을 함께 보여 주고 임의 매핑하지 않는다.
저장·삭제POST/PUT은 DTO 검증·중복/미존재 예외를 사용한다.구현 불일치백엔드 DELETE는 존재하지만 현재 고객 화면 소스에는 삭제 버튼/ConfirmModal이 보이지 않는다. 삭제 UI를 범위에 넣지 않는다.

04수락 기준
  • 조직 범위 고객만 행으로 표시되고 검색 결과 순서가 customerCode ASC다.
  • 필터·배지에 실제 공통코드명이 표시되며 원시 코드만 남지 않는다.
  • 신규 기본값과 backend 필수 필드가 일치하고 숫자·날짜 형식이 저장된다.
  • 중복 코드 409, 미존재 수정 404, validation 오류에서 입력을 보존한다.
  • 500건 초과 가능성을 확인하고 paged metadata와 화면 행 수를 대조한다.
  • 현재 화면의 삭제 부재와 customerCode 수정 semantics를 결정 후 구현한다.

명시해야 할 mismatch

구현 불일치DTO/service에는 paymentType query가 있으나 프론트 toolbar에는 businessStatus만 있다.

구현 불일치백엔드 DELETE는 등록되어 있지만 현재 고객 페이지에는 delete action/confirm이 없다.

구현 불일치압축된 form은 customerCode를 수정 payload에 포함할 수 있으나 service는 key 변경을 무시한다. 수정 코드 불변 여부를 UI에 명확히 표시한다.
