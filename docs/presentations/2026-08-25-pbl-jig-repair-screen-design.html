03Data control / SQL side effect

INSERT · APPEND · DELETE · UPDATE · source fact

INSERT  → DW_2.INSERTROW(0)
APPEND  → DW_2.INSERTROW(DW_2.GETROW())
신규 공통: dw_2.object.repair_request_date[row] = f_t_sysdate()
           dw_2.object.repair_date[row] = f_t_sysdate()
           dw_2.object.repair_sequence[row] = f_get_sequence('SEQ_JIG_REPAIR_SEQUENCE')
           dw_2.object.repair_status[row] = 'R'
           dw_2.object.repair_reason_code[row] = 'R'
           (dw_3 current row가 있으면 JIG_CODE 복사)

DELETE  → AcceptText → F_MSGBOX(1003) → DW_2.DELETEROW(row)
UPDATE  → DW_2.UPDATE() < 0 이면 ROLLBACK
           아니면 COMMIT + Update Complete

상태 action / SQL transaction

cb_process  text = "Repair OK"
             dw_2.object.repair_status[row] = 'P'
             F_MSGBOX(1170) → update → commit/rollback

cb_complete text = "Line Issue"
             dw_2.object.repair_status[row] = 'C'
             F_MSGBOX(1170) → update → commit/rollback

취소 branch는 f_retrieve()를 호출한다.
직접 REST mutation은 source에 없다.
신규 request-mode risk: 이 window의 INSERT/APPEND가 dw_3.getrow()를 확인해 JIG_CODE를 복사한다. 그러나 기본 request mode의 선택 source는 dw_1이고 dw_3는 reset/비표시일 수 있으므로, request-mode 신규가 dw_3를 참조하는 위험을 validation gate로 남긴다.

01P / C / R 상태와 신규 값 — 의미 충돌 map
값PB source 사실개발 DB code 정의설계 판정
Pcb_process 클릭 시 dw_2.object.repair_status[row] = 'P'; 버튼 text는 Repair OK.ISYS_BASECODE / REPAIR STATUS: P = 수리중.“Repair OK”와 DB 의미가 불일치한다. P의 업무 최종 의미를 source 설명으로 확정하지 않는다.
Ccb_complete 클릭 시 dw_2.object.repair_status[row] = 'C'; 버튼 text는 Line Issue.ISYS_BASECODE / REPAIR STATUS: C = 수리완료.“Line Issue”와 DB 의미가 불일치한다. C의 업무 action 이름을 임의로 보정하지 않는다.
RINSERT/APPEND 신규 row에 repair_status = 'R'와 repair_reason_code = 'R'를 대입한다.status: R = 수리중. reason code 정의는 1=조립불량, 2=파손, 3=기타; DB code에 reason R은 없다.신규 reason='R'는 DB reason code 정의와 충돌한다. 저장 전 업무/코드 결정 필요.

CURRENCY NOT NULL스키마에서 IMCN_JIG_REPAIR.CURRENCY VARCHAR2(3) nullable=N. 이 window의 INSERT/APPEND source에는 currency 대입이 없다. 반면 request master는 Gvs_currency를 대입한다.request-mode 신규를 실제 PB/DB에서 저장해 NOT NULL 오류 또는 기본값 경로를 원문으로 확인하고, 임의 default를 문서에 확정하지 않는다.
request-mode 신규가 dw_3를 참조하는 위험INSERT/APPEND가 if dw_3.getrow() >= 1일 때만 jig code를 복사한다. request 기본 mode는 dw_1이므로 신규 detail identity가 비어 있을 수 있다.request mode에서 선택 row → INSERT/APPEND → JIG_CODE / JIG_LOT_NO / ROWID와 DB row를 대조한다.
history 0건개발 DB 재현에서 inner join/effective join gate와 JIG_TYPE = :arg_jig_type가 함께 존재한다. PB는 '%'를 넘기므로 equality는 wildcard를 패턴으로 해석하지 않는다.LIKE로 바꾼 비교 query와 원본 query를 각각 실행해 0 ↔ 4 차이를 남긴다. 0을 업무상 무이력으로 승인하지 않는다.
hidden imagecb_7 Image Upload, cb_9 Image Delete, gb_4 Repair Image가 hidden. event는 image table과 BLOB를 update/delete한다.현재 UI에는 노출하지 않고, role check·key(jig/sequence/org)·commit/rollback을 source line으로 재확인한다.
상태/버튼 불일치PB 대입값 P/C/R, 버튼 text Repair OK/Line Issue, DB REPAIR STATUS 및 reason code가 서로 같은 업무 언어를 보장하지 않는다.업무 담당자 승인 전에는 label을 “source text”와 “DB code”로 분리하고 상태전이를 완료 판정으로 표현하지 않는다.

SELECT COUNT(*)
FROM IMCN_JIG_REPAIR r
INNER JOIN IMCN_JIG j
  ON r.JIG_CODE = j.JIG_CODE
 AND r.ORGANIZATION_ID = j.ORGANIZATION_ID
 WHERE (j.JIG_TYPE LIKE '%'
  AND r.JIG_CODE LIKE '%'
  AND r.JIG_LOT_NO LIKE '%'
  AND r.REPAIR_STATUS LIKE '%'
  AND r.REPAIR_REQUEST_DATE >= DATE '2021-01-01'
  AND r.REPAIR_REQUEST_DATE <= DATE '2026-08-26'
   AND r.ORGANIZATION_ID = 1)
    OR (r.JIG_CODE LIKE '%'
   AND r.JIG_LOT_NO LIKE '%'
   AND r.REPAIR_STATUS = 'R'
   AND j.JIG_TYPE LIKE '%'
   AND r.ORGANIZATION_ID = 1);
