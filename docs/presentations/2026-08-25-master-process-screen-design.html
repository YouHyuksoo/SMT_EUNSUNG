인증과 tenant

  • 활성ProcessController class-level JwtAuthGuard; 모든 process/equipment assignment/upload에 @OrganizationId() 전달.
  • 활성upload는 @UserId()를 service로 넘겨 relation 감사 컬럼을 채운다.
  • 확인assignment modal의 ProdLineSelect 원천 controller는 현재 소스에서 별도 class-level guard가 보이지 않으므로 global auth policy를 따로 점검한다.
Oraclemigration은 relation FK와 composite PK를 선언한다. live table/constraint/row count를 보지 않고 “SQL 적용 완료”라고 쓰지 않는다.
03위험·미구현·결정 필요

현재 source의 위험

  • 설비 이동assignOptions는 현재 공정에 배치되지 않은 모든 설비를 후보로 만든다. 다른 공정 설비를 선택하면 실제로 새 공정으로 이동한다. 차단/확인 정책이 UI에 없다.
  • 라인 변경updateEquipmentLine은 equipCode·조직만 찾고 route의 process membership를 검증하지 않은 채 LINE_CODE를 update한다.
  • 공정 삭제controller 주석과 달리 service는 repository.delete hard delete를 수행하며, 배치 설비 WORKSTAGE_CODE와 process-line relation을 먼저 해제하지 않는다.
  • relation UI공정-라인 relation은 Excel upload/list badge로만 다뤄지고 화면 수동 삭제·수정 action은 구현되어 있지 않다.
  • 표시 코드설비 grid 유형 badge는 EQUIP_TYPE, 설비 master selector는 MACHINE TYPE을 사용하므로 common-code alias 정합성을 확인한다.

수락 시나리오

  • 상단 공정 grid 60%, 하단 설비 grid 40%와 하단 최소 높이, editor 520px 및 assign modal을 rendered screen에서 확인한다.
  • sample .xlsx에서 sheet/header/type/start/number/duplicate/conflict 오류를 재현하고 결과 건수를 확인한다.
  • upload 전후 IP_PRODUCT_WORKSTAGE와 IP_PRODUCT_WORKSTAGE_LINE의 조직·복합키·행 수를 대조한다.
  • 설비 배치·이동·해제·라인 변경 후 실제 IMCN_MACHINE row와 grid/count를 함께 확인한다.
  • delete/409/404/API empty에서 선택 process와 editor 입력이 잘못 사라지지 않는지 확인한다.
