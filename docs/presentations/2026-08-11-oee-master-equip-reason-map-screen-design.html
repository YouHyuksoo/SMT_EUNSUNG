구분확정 동작화면·서버 주의
설비 키신규는 설비 picker에서 단일 선택. 이미 연계된 설비는 신규 생성 차단.수정에서는 machineCode read-only. machine name/type/line/process는 참조 표시.
사유 선택사용중(USE_YN='Y') 사유를 복수 체크해 grid에 추가한다.현재 page는 전체 list를 받은 뒤 client filter한다. 같은 code는 merge 시 제거.
최소 입력설비 1건과 사유 1건 이상이 있어야 저장한다.사유 선택 grid에서 check 후 선택삭제 가능. 선택삭제는 local form만 변경.
저장 semantics헤더 upsert 후 상세를 DELETE하고 선택 순서대로 재INSERT한다.backend transaction이며 codes trim/empty 제거·중복 제거, sort 1부터 기록.
목록 사유 보기행의 “사유 n건”을 누르면 읽기 modal에서 code/name/type/OEE/use를 표시한다.미사용 사유는 muted로 보이며, 목록 search는 사유 code/name도 포함한다.
삭제행 삭제 icon → 설비명·매핑 건수 확인 modal → header/detail 전체 삭제.machineCode URL encode. 실패 시 toast, 성공 후 목록 reload.

03DB·계산·Acceptance·Mismatches
영역계약·처리검증·주의
헤더IP_EQUIP_DOWNTIME_MAP(MACHINE_CODE, ORGANIZATION_ID, ENTER/LAST_MODIFY*)설비별 매핑 존재 여부와 감사 주체
상세IP_EQUIP_DOWNTIME_MAP_DTL(MACHINE_CODE, REASON_CODE, ORGANIZATION_ID, SORT_NO, ENTER*)복합 PK. 저장 순서가 SORT_NO 1..n
조회 joinheader/detail → IMCN_MACHINE → IP_EQUIP_DOWNTIME_REASON left joins사유명이 없어도 code row를 구성할 수 있는지 실제 DB 확인
계산OEE 계산 없음. list는 reason count/label/정렬만 제공한다.이 매핑이 모바일/집계에 소비되는 경로는 별도 검증
정렬machineCode, SORT_NO, DISPLAY_ORDER, reasonCodeUI는 API가 준 reasons 순서를 보존
확인 필요 · @Public/하드코드 조직EquipReasonMapController가 @Public()이며 Guard/조직 decorator가 없다. EquipReasonMapService는 list/upsert/remove 모두 const ORG = 1, 기본 사용자 ADMIN을 사용한다. 반면 설비 picker의 EquipMasterController는 @OrganizationId()를 사용하므로 참조 API와 매핑 API의 tenant 경계가 다르다.

Acceptance

  • 설비별 목록과 사유 건수가 맞다.
  • 검색이 설비·사유 양쪽에서 동작한다.
  • 신규 중복 설비가 차단된다.
  • 복수 선택·중복 제거·선택삭제가 동작한다.
  • 저장 후 header/detail 전체가 원하는 순서로 재조회된다.
  • 삭제 확인 대상과 실제 삭제 범위가 일치한다.

Mismatches

  • picker는 API에 USE_YN filter를 전달하지 않고 client filter.
  • 설비 list response wrapper shape를 두 방식으로 추정.
  • 변경/닫기 dirty guard와 partial failure UI 없음.
  • 매핑 header가 모바일 OEE resource와 자동 FK가 아님.
  • API 공개·ORG=1은 운영 tenant 계약과 충돌 가능.
