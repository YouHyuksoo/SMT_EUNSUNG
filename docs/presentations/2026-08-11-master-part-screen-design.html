01요구사항 및 사용자 흐름

목적

조직 범위의 품목을 검색하고, 공통코드 기반 분류·단위·표시여부와 포장/유효기간/적재정보를 유지한다.

목록은 최대 5,000건 요청, 정렬은 ITEM_CODE ASC다.

사용자·입력

인증된 기준정보 담당자. itemCode, 품번, 품목명, 품목유형·분류, 수량·기간, 사진을 입력한다.

ITEM_TYPE · ITEM_CLASS · ITEM_UOM은 자유코드가 아니라 ISYS_BASECODE 선택.

핵심 결과

LIST 필터 목록 / FORM 우측 480px 패널 / IMAGE 업로드·삭제 / SYNC ERP 동기화.

저장 성공 후 목록을 다시 조회하고 패널을 닫는다.

03비즈니스 규칙
구분규칙화면·서버 처리
키·필수itemCode는 신규 필수·수정 불변. itemNo, itemName, itemClass도 저장 전 필수.패널 저장 버튼은 네 값이 없으면 비활성화. 서버 DTO는 길이와 타입을 다시 검사한다.
공통코드itemType/itemClass/itemUom은 공통코드, mesDisplayYn은 Y/N.그리드는 ComCodeBadge, 필터는 ComCodeSelect/UseYnSelect로 표시한다.
수량·기간박스·최소불출·LOT·안전재고·유효기간·연장기간·팔레트 구성 단위는 0 이상 수량이다.QtyInput으로 숫자 입력. 서버 DTO의 @Min(0)이 최종 방어선이다.
삭제입하·입고·재고·롯트·BOM·생산계획 참조가 하나라도 있으면 삭제하지 않는다.행 삭제 확인 후 서버가 참조 건수를 조회하고 409를 반환한다. 실패 시 품목을 유지한다.
사진·동기화사진은 JPEG/PNG/GIF/WebP, 5MB 이하. ERP 동기화는 전체 품목을 추가·변경한다.사진은 별도 multipart API. ERP 동기화는 확인 모달 후 /interface/inbound/item-master를 호출한다.

03DB·검증·완료 기준

DB / 서버 불변식

  • PK는 (ITEM_CODE, ORGANIZATION_ID); 모든 목록·변경·삭제는 조직 조건을 포함한다.
  • 생성 시 중복 code는 409. DTO는 문자열 길이, Y/N, 0 이상 숫자를 검증한다.
  • 삭제 전 MAT_ARRIVALS, MAT_RECEIVINGS, MAT_STOCKS, MAT_LOTS, BOM_MASTERS, PROD_PLANS를 검사한다.
  • 사진은 이미지 MIME과 5MB를 서버에서 재검증한다.

수락 시나리오

  • 검색·유형·MES 표시 필터가 query와 동일하게 결과를 바꾼다.
  • 신규 저장 → 목록 행 생성, 수정 → 행 값 갱신, 사진 업로드/삭제 → imageUrl 동기화.
  • 필수 누락·음수·중복 code는 저장하지 않고 오류를 표시한다.
  • 참조 품목 삭제는 차단되고 “MES_DISPLAY_YN을 N으로 변경” 안내를 보존한다.
  • ERP 동기화 성공/실패 메시지와 재조회가 동작한다.
04현재 구현 불일치 및 백엔드 전용 동작

불일치UI·DTO·DB

  • CreatePartDto에는 drawNo, leadTime, tactTime, toleranceRate, isSplittable가 있지만 현재 PartFormPanel은 렌더링·payload 전송을 하지 않는다.
  • 폼 라벨 “리비전”의 PartFieldHelp 매핑은 실제 ID_ITEM.ABC_GRADE다. 업무 의미를 변경하지 말고 확인 항목으로 남긴다.
  • UI 사진은 “품목 사진”이지만 엔티티 컬럼명은 FEEDER_LAYOUT_COMMENTS다.

백엔드 전용현재 페이지에서 직접 호출하지 않는 API

  • GET /master/parts/types/:type: 사용 품목만 유형별 반환.
  • GET /master/parts/code/:itemCode 및 GET /master/parts/:id: 단건 조회.
  • 상세 API는 이미지 삭제 전 서비스에서 사용되지만 목록 화면의 별도 상세 action은 없다.
  • ERP 동기화는 PartController가 아니라 interface route로, 권한·실데이터 영향 확인을 별도 검증한다.
