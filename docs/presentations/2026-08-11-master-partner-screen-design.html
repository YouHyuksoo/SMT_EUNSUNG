01요구사항과 사용자

목적

확인공급사 코드·명칭·사업자·대표자·주소·연락처·담당자·사용 상태를 관리한다. 현재 화면의 거래처 유형은 SUPPLIER로 고정된다.

고객·외주·운송사까지 확장하는 계약은 이 화면에 포함하지 않는다.

사용자·권한

추정구매/자재 또는 기준정보 관리자. 소스에 역할명은 없고 controller의 @OrganizationId()가 조직 범위를 받는다.

확인인증된 목록·변경 API로 설계된 경로다.

핵심 결과

텍스트 검색과 사용여부 필터로 공급사를 찾는다.

미사용 행은 빨간 글씨, 상태 컬럼은 Y/N 배지로 표현한다.

03업무 규칙·범위 경계

유형생성 DTO가 partnerType=SUPPLIER만 허용하며 form도 읽기 전용 SUPPLIER를 표시한다.DTO에는 유형 조회·통계 API가 있으나 다른 유형을 생성하지 않는다.
필수·키partnerCode 신규 필수·수정 불변, partnerName 필수. 코드 최대 20, 명칭 최대 100.수정 URL은 partnerCode다. 중복은 조직 범위에서 409.

검색·표현코드·명칭·사업자·담당자 검색, useYn=Y/N 필터. 미사용 행은 빨간 텍스트.컬럼 filter와 export는 DataGrid 공통 동작으로 유지한다.

04수락 기준
  • 조직 컨텍스트 밖 공급사가 목록·단건·변경에 섞이지 않는다.
  • SUPPLIER 고정 유형과 코드 라벨이 일관되며 코드 수정은 차단된다.
  • Y/N 필터, 미사용 red row, column filter/export가 유지된다.
  • 중복/validation/네트워크 오류에서 입력을 보존하고 성공 후 재조회한다.
  • 삭제 전 대상명과 hard/soft semantics를 명시하고 실제 DB 행 변화를 확인한다.
  • DTO의 미노출 필드와 다른 거래처 유형은 설계 범위 밖으로 남긴다.

명시해야 할 mismatch

구현 불일치페이지/주석은 soft delete라고 하지만 supplierRepository.delete()가 실행된다.

구현 불일치DTO의 qualityGrade/inspectionMode/remark는 form에 없고 service도 quality=null, inspection=NORMAL, remark=null로 반환한다.

구현 불일치거래처 유형 확장은 DTO에 일부 흔적만 있고 create DTO는 SUPPLIER만 허용한다. 고객·외주·운송사를 임의로 추가하지 않는다.
