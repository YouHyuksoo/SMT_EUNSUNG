# 설비 운영 현황 (OEE_EQUIP_OPS_STATUS)

- 작성일: 2026-08-27
- 메뉴: OEE관리 > 설비 운영 현황 · `/oee/equip-ops-status`
- 선행: [ADR 0002](../adr/0002-equip-downtime-machine-scoped.md) (비가동을 설비 기준으로 전환)

## 목적

설비마스터 전체의 가동 상태를 한눈에 보고, 라인 또는 설비 단위로 비가동을
시작/종료한다. 한 화면 안에 탭 두 개로 나눈다.

- **모니터링 탭** — 설비 120대 목록 + 현재 상태 + 행별 비가동 관리
- **비가동 처리 탭** — 라인/설비 선택(바코드) 후 지표·현재상태·이력을 보며 처리

## 확인된 데이터 현실

구현 전 실 DB(ES_JSIDC)에서 확인한 사실이다. 설계가 이 위에 서 있다.

| 항목 | 확인 결과 |
|---|---|
| 설비마스터 | `IMCN_MACHINE` 120대 (org 1) |
| 설비유형 | `MACHINE_TYPE` 9종, 코드명은 `ISYS_BASECODE`의 `CODE_TYPE='MACHINE TYPE'`에 존재 |
| 적용공정 | `WORKSTAGE_CODE` 10종, `IP_PRODUCT_WORKSTAGE`에 이름 존재 |
| 모델 | `MACHINE_MODEL_NAME` 120건 채워짐. `MODEL_NAME`은 전부 NULL — 쓰지 않는다 |
| 라인마스터 | `IP_PRODUCT_LINE` 18건 |
| **설비↔라인 매핑** | **없음.** 120대 전부 `LINE_CODE='*'` |

설비↔라인은 `IMCN_MACHINE_DAILY_OPERATION`(0건), `IP_PRODUCT_RUN_CARD`
(`MACHINE_CODE` 37,354건 NULL)에도 없다. 라인 기능은 만들되 현재는 항상
"배정된 설비 없음"으로 나온다.

> 공통코드는 `ISYS_CODE_MASTER`가 아니라 **`ISYS_BASECODE`**다. 조사 중 한 번
> 틀렸던 지점이라 적어둔다.

| 12 | 라인 일괄 종료 사유는 **공통 1개로 덮어쓰기** | 단건 화면의 "종료 시 사유 필수" 규칙 유지 |

## 화면 구성

### 모니터링 탭

조회조건 — 설비유형 / 적용공정 / 상태(전체·비가동·정상) / 통합검색(설비코드·명)

| 컬럼 | 소스 |
|---|---|
| 설비코드 | `MACHINE_CODE` |
| 설비명 | `MACHINE_NAME` |
| 유형 | `MACHINE_TYPE` → `ISYS_BASECODE` 이름 |
| 적용공정 | `WORKSTAGE_CODE` + `IP_PRODUCT_WORKSTAGE.WORKSTAGE_NAME` |
| 모델 | `MACHINE_MODEL_NAME` |
| 상태 | 진행중 비가동 유무 → `비가동`/`정상` 배지 |
| 비가동 처리 | 버튼 → 우측 슬라이드 패널(`EquipDowntimePanel`) |

## 검증 결과 (2026-08-27)

백엔드 API는 실 DB(ES_JSIDC)로 전 경로를 확인했다.

| 호출 | 결과 |
|---|---|
| `machines` | 120대 · 유형명 `코팅 설비` 정상 · 유형필터 37대 · 검색 2대 |
| `lines` | 18건 · `machineCount` 전부 0 (매핑 부재, 예상대로) |
| `summary` | `{downMinutes: 103, stopCount: 1}` |
| `monthly` | 총 4회 / 107분 |
| `bulk START` | 이미 비가동 1대 skip, 정상 1대 시작 |
| `bulk END` (사유 없음) | 400 `종료 시 비가동 사유를 선택하세요` |
| `bulk END` (사유 있음) | 2대 종료 |
| `bulk` 라인(설비 0대) | `targets: 0` |

검증용 행 4건은 삭제해 기존 3건 + 사용자 진행중 1건 상태로 되돌렸다.

화면은 `/oee/equip-ops-status` HTTP 200, 컴파일 정상. 다만 `(authenticated)` 레이아웃이
클라이언트 인증 후 본문을 그리므로 curl로는 내용 검증이 불가하다 — 브라우저 확인이 필요하다.

## 알려진 lint 상태

신규 파일에 `Calling setState synchronously within an effect` 3건이 남는다
(`page.tsx` 1 · `DowntimeTab.tsx` 2). 전부 `useEffect(() => { load(); }, [load])`
형태로, 형제 화면 `equip-work-result/page.tsx`가 쓰는 것과 같은 관용구다.
이 규칙은 저장소 전체에서 이미 실패 중이라 주변 스타일에 맞췄다.
정리하려면 저장소 차원에서 `useApiQuery`(TanStack Query)로 옮기는 별도 작업이 맞다.
