# 공정 엑셀 업로드 설계

## 목표

공정관리 화면에서 생산팀별 공정 엑셀을 드래그앤드롭하여 공정마스터와 공정별 적용 라인을 한 번에 등록한다. 기존 생산실적·라우팅 테이블이 참조하는 공정마스터 키는 유지하고, 다중 라인 관계는 별도 테이블로 정규화한다.

## 확정된 업무 규칙

- 공정마스터 키는 기존 `(WORKSTAGE_CODE, ORGANIZATION_ID)`를 유지한다.
- 신규 공정-라인 관계 키는 `(ORGANIZATION_ID, WORKSTAGE_CODE, WORKSTAGE_TYPE, LINE_CODE)`다.
- 공정유형 표시값은 `일반=I`, `최종=L`, `검사=Q`로 변환한다.
- 시작공정구분은 공백 제거와 대문자화 후 `Y` 또는 `N`만 허용하며 공정마스터 `WORKSTAGE_START_YN`에 저장한다.
- 동일한 공정-라인 복합키 행은 파일 안에서 한 건으로 합친다.
- 같은 공정코드의 공정명·공정유형·시작공정구분이 행마다 하나라도 다르면 파일 전체를 거부한다. 이 공정마스터 일관성 검증은 공정-라인 복합키 중복 제거보다 먼저 수행하여 임의의 행 값이 선택되지 않게 한다.
- 생산 1팀 업로드 부서는 `1000`(생산관리), 생산 2팀은 `2500`(2층 생산)이다.
- 정렬순서는 공정코드의 숫자부를 사용한다. 숫자부가 없으면 검증 오류로 거부한다.
- 공정마스터의 `LINE_CODE`는 다중 라인 관계를 나타내는 `*`로 저장한다.
- 기존 공정을 재사용할 때 공정명·공정유형·시작공정구분·부서가 파일과 모두 같고 `LINE_CODE='*'`인 경우만 허용한다. 하나라도 다르면 기존 값을 덮어쓰지 않고 전체 업로드를 거부한다.
- 업로드 일반 기능은 존재하지 않는 부서나 라인을 자동 생성하지 않고 오류로 거부한다.
- 이번 초기 데이터 적용에 한해 승인된 라인 `21~24`를 먼저 라인마스터에 등록한다.

## 데이터 모델

### 기존 공정마스터

`IP_PRODUCT_WORKSTAGE`의 기존 PK와 이를 참조하는 다음 FK는 변경하지 않는다.

- `IP_ASSEMBLY_RESULT`
- `IP_PRODUCT_RESULT`
- `IP_PRODUCT_REWORK_RESULT`
- `IP_PRODUCT_ROUTING`

업로드 시 공정코드별로 공정마스터 한 건을 생성하거나 기존 건을 재사용한다. 기존 건의 이름·유형이 파일과 충돌하면 묵시적으로 덮어쓰지 않고 업로드를 거부한다.

### 신규 공정-라인 관계

`IP_PRODUCT_WORKSTAGE_LINE`을 추가한다.

| 컬럼 | 역할 |
|---|---|
| `ORGANIZATION_ID` | 조직 격리 및 PK |
| `WORKSTAGE_CODE` | 공정코드 및 PK |
| `WORKSTAGE_TYPE` | 공정유형 및 PK |
| `LINE_CODE` | 적용라인 및 PK |
| `ENTER_BY`, `ENTER_DATE` | 등록 감사정보 |
| `LAST_MODIFY_BY`, `LAST_MODIFY_DATE` | 수정 감사정보 |

제약조건:

- PK: `(ORGANIZATION_ID, WORKSTAGE_CODE, WORKSTAGE_TYPE, LINE_CODE)`
- FK: `(WORKSTAGE_CODE, ORGANIZATION_ID)` → `IP_PRODUCT_WORKSTAGE`
- FK: `(LINE_CODE, ORGANIZATION_ID)` → `IP_PRODUCT_LINE`
- `WORKSTAGE_TYPE`은 부모 공정의 유형과 일치해야 하며 서비스 트랜잭션에서 검증한다.

`WORKSTAGE_TYPE`을 관계 PK에 포함하는 것은 승인된 업무 식별키를 그대로 보존하기 위함이다. 관계가 존재하는 공정의 유형 변경은 관계 식별키를 무효화하므로 일반 수정 API에서 거부한다. 유형 변경이 필요하면 관계를 먼저 제거한 뒤 공정을 수정하고 다시 업로드한다.

### 신규 라인 초기 데이터

조직 `1`에 다음 라인을 추가한다. 필수 구분값은 기존 라인 `19~20`과 동일하게 적용한다.

| 라인코드 | 라인명 | LINE_DIVISION | LINE_PRODUCT_DIVISION | LINE_STATUS | ACTIVE_YN |
|---|---|---|---|---|---|
| 21 | 성능검사기 | W | FIXED | N | N |
| 22 | COATING MACHINE | W | FIXED | N | N |
| 23 | JETTING MACHINE | W | FIXED | N | N |
| 24 | ROUTER | W | FIXED | N | N |

## 백엔드 설계

공정 모듈에 multipart 엑셀 업로드 엔드포인트를 추가한다. 요청은 엑셀 파일과 `departmentCode`를 받으며 조직ID는 인증 컨텍스트에서만 가져온다. `departmentCode`는 공정마스터 `DEPARTMENT_CODE`에 저장한다.

처리 순서:

1. 첫 번째 `공정마스터` 시트를 읽는다.
2. 필수 헤더 `공정코드`, `공정명`, `공정유형`, `시작공정구분`, `적용라인코드`를 검증한다.
3. 값을 정규화하고 공정유형을 변환한 뒤, 동일 공정코드의 공정명·유형·시작구분 일관성을 검증한다. 검증 통과 후 정렬순서를 계산하고 파일 내 복합키 중복을 제거한다.
4. 요청 조직의 부서·라인 존재 여부와 공정마스터 충돌을 일괄 조회한다. 기존 공정은 공정명·공정유형·시작공정구분·부서가 모두 같고 `LINE_CODE='*'`일 때만 재사용한다.
5. 하나의 TypeORM 트랜잭션에서 공정마스터와 공정-라인 관계를 저장한다.
6. 동일한 기존 관계는 건너뛰고, 신규 관계만 추가한다.
7. 성공 시 입력행·중복제거·공정생성·공정재사용·관계생성·관계건너뜀 건수를 반환한다.

검증 오류는 행 번호와 원본 값이 포함된 목록으로 반환한다. 파일 내 오류나 DB 기준정보 오류가 하나라도 있으면 저장하지 않는다. Oracle 오류는 서버 로그에 원문을 보존하고 사용자 응답은 기존 예외 처리 규칙을 따른다.

목록 조회 응답에는 공정별 `appliedLineCodes: string[]`를 추가한다. 서비스는 현재 페이지의 공정코드들에 해당하는 관계를 한 번에 조회해 라인코드 순으로 묶으며, 공정별 추가 쿼리를 발생시키지 않는다.

## 프론트엔드 설계

공정관리 헤더에 `엑셀 업로드` 버튼을 추가한다. 모달은 다음 요소만 제공한다.

- `.xlsx` 파일 드래그앤드롭/선택
- 공용 부서 선택 컴포넌트
- 선택 파일명과 행 검증 요약
- 업로드 실행·취소 버튼
- 성공/중복/건너뜀 건수 또는 행별 오류 목록
- 공정 목록의 적용라인 코드 열

브라우저의 파일 내용은 사용자 피드백을 위한 헤더·행수 확인에만 사용한다. 최종 검증과 변환은 백엔드가 다시 수행한다. 성공 후 모달을 닫고 공정 목록 및 선택 상태를 재조회한다. 공정 목록은 `appliedLineCodes`를 코드 배지로 표시하여 업로드 관계를 즉시 확인할 수 있게 한다.

## 초기 두 파일 적용

- 생산 1팀: 원본 60행, 공정 5건, 공정-라인 관계 60건, 부서 `1000`.
- 생산 2팀: 원본 36행, 복합키 중복 30행 제거, 공정 6건, 공정-라인 관계 6건, 부서 `2500`.
- 두 파일은 UI 업로드 기능을 통해 한 파일씩 적용한다.
- 동일 공정코드가 두 파일 사이에서 충돌하면 두 번째 업로드는 전체 거부한다.

## 테스트 및 검증

TDD 순서로 다음 회귀를 먼저 실패시킨 뒤 최소 구현으로 통과시킨다.

- 엔티티/DDL의 PK·FK 구조
- 한글 헤더와 공정유형 변환
- 파일 내 복합키 중복 제거
- 동일 공정코드의 이름·유형 충돌 거부
- 기존 공정의 시작구분·부서·레거시 라인값 충돌 거부
- 조직 컨텍스트만 사용하는 업로드 API와 인증 Guard 메타데이터
- 트랜잭션 전체 롤백
- 기존 관계 건너뛰기와 결과 건수
- 프론트 업로드 버튼·부서 선택·multipart 계약
- 목록 응답의 적용라인 일괄 조회와 렌더링

완료 검증 순서:

1. 백엔드 focused Jest와 TypeScript typecheck
2. 프론트 구조 테스트, typecheck, lint
3. Oracle DDL 사후 PK/FK와 라인 `21~24` 확인
4. 업로드 전후 Oracle 기대 건수 확인
5. 인증된 백엔드 API와 프론트 프록시 응답 확인
6. 공정관리 화면에서 공정과 적용 라인 렌더링 확인

DB 변경과 업로드는 각각 사전 건수와 사후 건수를 기록한다. 실패 시 미완료 기록을 `docs/reports/`에 남긴다.
