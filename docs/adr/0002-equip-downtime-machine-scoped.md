# 0002. 설비비가동을 작업지시가 아닌 설비 기준으로 다룬다

- 결정일: 2026-08-27
- 상태: 승인
- 대상: `IP_EQUIP_DOWNTIME_RESULT`, `/oee/equip-work-result`

## 배경

설비비가동은 `IP_EQUIP_DOWNTIME_RESULT`에 저장되며 PK가 `(RUN_NO, DT_SEQ, ORGANIZATION_ID)`,
`RUN_NO`는 NOT NULL이다. 즉 모든 비가동은 작업지시에 매달려 있어야 한다.

그런데 현장에서는 작업지시와 무관하게 설비가 멈춘다. 또한 이미 코드 안에서도
설비 가동/정지 배지는 `RUN_NO`가 아니라 `MACHINE_CODE` 기준으로 집계하고 있었다
(`work-result.service.ts`의 `openDowntime` 서브쿼리). 저장 구조와 실제 판정 기준이
어긋나 있는 상태였다.

작업지시 기준 조회를 유지한 채 작업지시 없는 비가동만 추가하면, 같은 설비에
"작업지시로 시작한 진행중 비가동"과 "작업지시 없이 시작한 진행중 비가동"이 동시에
존재할 수 있고 어느 화면에서도 둘 다 보이지 않는다.

## 결정

1. 비가동의 주체는 **설비**다. `RUN_NO`는 비가동이 어떤 작업 중에 발생했는지 기록하는
   선택적 맥락 정보로 격하한다.
2. `RUN_NO`를 nullable로 바꾸고 PK를 `(DT_SEQ, ORGANIZATION_ID)`로 재설계한다.
   `DT_SEQ`는 `SEQ_IP_EQUIP_DOWNTIME` 시퀀스에서 채번한다.
3. 비가동 이력 조회와 진행중 이벤트 판정은 작업지시 선택 여부와 무관하게
   `MACHINE_CODE` 기준으로 통일한다.
4. 작업지시로 시작한 비가동을 설비만 선택한 화면에서 종료할 수 있다. 종료는
   `DT_SEQ` 단독으로 식별한다.

## 대안과 기각 사유

**센티널 `RUN_NO`** (예: `'@NOWO'`) — DDL 없이 즉시 적용 가능하지만 `RUN_NO` 컬럼에
실제 작업지시가 아닌 값이 섞인다. 이후 `RUN_NO` 기준 조인·집계가 전부 센티널을
알아야 하는 부채가 남는다. 기존 데이터가 3건뿐이라 지금 스키마를 바로잡는 비용이
가장 낮다고 판단해 기각했다.

## 결과

- 기존 3건의 `DT_SEQ`가 `1,1,2`로 중복이므로 PK 변경 전 재채번이 필요하다.
- 기존 PK의 선두 컬럼 `RUN_NO`가 더 이상 주 조회 경로가 아니므로
  `MACHINE_CODE` 인덱스를 추가한다.
- 작업지시별 비가동 목록이 필요해지면 `RUN_NO` 조건을 다시 붙이면 된다 — 데이터는 남는다.
