### 3.3 M1의 확인된 사용자 흐름

1. 후면 카메라로 QR 또는 바코드를 스캔한다.
2. 카메라·권한·브라우저 문제 시 설비코드를 수동 입력한다.
3. 설비코드, 설비명, 라인 정보를 확인한다.
4. 서버에 저장된 현재 상태와 변경 대기 상태를 구분한다.
5. 비가동 전환 시 승인된 사유를 선택한다.
6. 저장 중 중복 제출을 막는다.
7. 성공 응답 후에만 저장 상태를 갱신한다.
8. 실패하면 입력 초안을 유지하고 재시도를 제공한다.
9. 미저장 변경이 있으면 재스캔 전에 처리 여부를 확인한다.

이 화면은 실제 설비를 제어하거나 긴급정지를 수행하는 화면이 아니라 MES 이력을 기록하는 화면이다.

### 3.4 산업용 UI 기준

- 10.1인치 Android 태블릿, 1920x1200 또는 1280x800, 가로 모드
- 터치 타깃 최소 `64dp`, 주요 버튼 높이 최소 `72dp`, 인접 행동 간격 최소 `12dp`
- 화면 여백 `24dp`, 구성요소 간격 `16dp`, 8dp 그리드
- 주요 상태값 `36~48sp`, 제목 `24sp`, 본문·버튼 `18~20sp`, 최소 글자 `14sp`
- 상태는 색상만 사용하지 않고 텍스트와 아이콘을 병기
- Wise 디자인은 세이지 배경, 흰 카드, 제한적 라임 강조만 참고
- 정상·경고·비가동 의미색과 현장 가독성이 브랜드 스타일보다 우선

## 4. 확인된 구현 격차

- M1의 설비와 비가동 사유는 로컬 Mock 배열이다.
- 저장은 React 상태와 토스트만 변경하며 서버에 기록되지 않는다.
- 백엔드 OEE 컨트롤러에 설비 조회와 비가동 저장 API가 없다.
- 화면의 `RUNNING/STOPPED`와 백엔드의 `RUN/DOWN` 관계가 정의되지 않았다.
- QR 값이 설비코드인지 OEE 리소스 참조코드인지 정해지지 않았다.
- 서버 기준 시각, 작업자 식별, 교대 경계, 권한, 동시성 정책이 미정이다.
- 오프라인 저장은 idempotency 계약이 없으므로 현재는 block-and-retry가 안전한 기본안이다.
- 기존 OEE 컨트롤러의 `@Public()`은 쓰기 화면의 서버 권한 요구와 충돌할 수 있다.

3. QR/바코드가 식별하는 기준 키
4. 비가동 기록을 기존 OEE 구간으로 저장할지 별도 설비 이벤트로 저장할지
5. 상태 용어와 `RUNNING/STOPPED` ↔ `RUN/DOWN` 매핑
6. 작업자 인증과 서버 권한 정책
7. 서버 기준 시각과 교대 경계 정책
8. 기존 MainLayout 사용, 전용 태블릿 셸, 또는 혼합 셸 중 방향
9. 오프라인 시 저장 차단·재시도만 제공할지 큐 동기화를 설계할지
