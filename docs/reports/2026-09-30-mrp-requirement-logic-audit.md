# 자재 소요량·발주량 산출 로직 감사 (477·478)

- 작성일: 2026-09-30
- 작성 계기: 477·478 이관 직후 산출 로직의 정확성을 PB 원문과 줄단위로 재대조
- 대상: `apps/backend/src/modules/purchase/requirement-plan.service.ts`,
  `apps/backend/src/modules/purchase/order-plan.service.ts`

## 요약 (결론 먼저)

- 구멍 **7개**를 찾아 전부 고쳤다. 함께 확인한 설계 질문 1개는 사용자가 확정해
  닫혔다 (477 은 순소요, 478 이 재고를 뺀다 — 현재 동작이 맞다).
- 고친 것 중 **두 개는 그대로 두면 기능이 매번 실패**했다:
  `F_GET_DELIVERY_DATE` 를 인자 4개로 불렀고(실제 2개), 리드타임 방향이 반대였다.
  둘 다 화면 기본 켜짐 옵션이라 발주계획 생성이 전부 깨진다.
- 식별자 6개와 **쓰기 문장 14개를 은성 DB 에서 `DBMS_SQL.PARSE` 로 확인했다** —
  실행하지 않고 문법·테이블·컬럼·함수 인자 수를 해석시켰다. 전부 통과.
- **원장에 실제로 써 보지는 않았다.** 발주 계열 표는 전부 0행이라(2020년 구축 이후
  미사용) 현장 실사용 확인이 남아 있다.

## 고친 구멍

### 477 자재소요량

| 구멍 | 그대로 두면 |
|---|---|
| BOM 전개 실패가 조용히 넘어감 | `PKG_DESIGN.BOM_EXPLOSION` 이 음수를 주면 `WHERE SESSION_ID = -1` 이 0행을 넣고 지나가, **그 품목의 소요량이 말없이 빠진다**. PB 477 은 검사하지 않지만 478 생성기는 검사한다 — 그쪽에 맞췄다. |
| 주문수량 NULL | `MODEL_UNIT_QTY * NULL` 이 NULL 이 되고 `IM_ITEM_REQUIRMENT_PLAN_TEMP.REQUIRMENT_QTY` 는 NOT NULL 이라 ORA-01400 으로 떨어진다. 어느 품목인지 알 수 없었다. |
| 전개 임시행 누수 | `BOM_EXPLOSION` 은 스스로 커밋하므로 우리 롤백으로 `ID_ENG_BOM_TEMP` 행이 지워지지 않는다. 그 표에 2020년부터 세션 7만 개·330만 행이 쌓인 이유다. 실패한 세션만 예외 처리에서 지운다. |

### 478 자재발주계획

| 구멍 | 그대로 두면 |
|---|---|
| 올림 잉여가 재고 풀로 안 돌아감 | 최소주문량·포장단위로 올린 잉여를 PB 는 `IM_ITEM_INVENTORY_GEN` 에 써 넣어 같은 자재의 뒤 계획줄이 덜 발주하게 한다. 되돌리지 않으면 **줄마다 올림이 반복돼 과다 발주**된다. |
| 리드타임 방향이 반대 | 자재는 생산 시작 **전에** 들어와야 하므로 납기를 앞으로 당긴다 (PB: `DELIVERY_DATE - ID_ITEM.MANUFACTURE_LEADTIME`). 뒤로 밀고 있었고 화면 설명도 거꾸로였다. |
| 작업일 보정을 리드타임과 한 덩어리로 묶음 | PB 는 별개 체크박스이고 `F_GET_DELIVERY_DATE` 를 **인자 2개**로 부른다. 나는 4개로 불렀다 → ORA-06553. |

### 478 발주 확정 — 네 곳이 어긋나 있었다

| 구멍 | 그대로 두면 |
|---|---|
| 계획을 지웠다 | PB 는 `PURCHASE_ORDER_STATUS` 를 `'Y'` 로 바꿀 뿐이다. 지우면 **어느 계획에서 나온 주문인지 되짚을 수 없다.** 480 주문예정도 같은 이유로 기록을 남긴다. |
| 주문번호를 새로 채번했다 | PB 는 계획이 들고 있는 `ORDER_NO`(`TA+YYMMDD+일련번호`)를 그대로 쓴다. 새로 매기면 계획과 주문이 끊긴다. |
| `ORDER_GROUP_NO` 를 비워 뒀다 | **481 자재주문관리가 그 값으로 발주그룹 합계를 낸다.** 비면 그 화면의 그룹 집계가 나오지 않는다. |
| 납품구분 없는 계획도 넘겼다 | `DELIVERY` 가 비면 단가·통화가 안 붙은 계획이라는 뜻이다. PB 처럼 `LINE_TYPE <> 'T'` · `DELIVERY IS NOT NULL` 로 막고, 넘어가지 못한 건수를 화면에 알린다. |

## 확정된 설계 — 477 은 순소요, 478 이 재고를 뺀다

전개식은 원래 수량을 쓴다:

```
REQUIRMENT_QTY = MODEL_UNIT_QTY * ORDER_QTY
```

즉 477 이 내는 것은 **순소요**(재고를 빼지 않은 총 필요량)이고, 재고 차감은 478
자재발주계획이 한다. PB 도 동일하다 (`MODEL_UNIT_QTY * :LVF_ORDER_QTY`).

**사용자 확정(2026-09-30): "순소요는 재고 감안 안한게 맞고 발주는 재고를 빼는게 맞아".**
현재 동작이 맞으므로 계산식은 바꾸지 않았다.

다만 477 의 버튼 이름이 `재고 반영` 이어서 소요량이 바뀌는 것처럼 읽혔다. 화면 문구를
고쳤다:

- 버튼 `② 재고 반영` → `② 재고 표시`
- 툴팁·확인 모달에 "소요량 숫자는 바뀌지 않습니다 — 순소요는 재고를 감안하지 않고,
  재고 차감은 자재발주계획(478) 이 합니다" 를 적었다.
- 헤더에 "순소요를 산출합니다 (재고를 빼지 않은 총 필요량)" 을 밝혔다.

이 버튼이 채우는 재고 컬럼은 참고 표시다. PB 에서 실재고를 읽는
`UPDATE IP_PRODUCT_INV_4_REQUIREMENT ... INVENTORY_QTY` 가 주석 처리돼 있어 지금은
안전재고만 채워진다 — 이것도 PB 동작 그대로 두었다.

## 검증

이 PC 에서는 외부 주소(`ESDBext`, 61.105.35.54)가 아니라 **내부 LAN 주소 `ESDB`
(192.168.175.100:1521/XE)로 접속한다** — 같은 DB 다. 외부 주소 타임아웃은 장애가 아니라
접속 경로 차이다.

문장은 `DBMS_SQL.PARSE` 로 **실행하지 않고** 확인했다 — Oracle 이 parse 단계에서 함수
인자 수와 컬럼명을 해석하므로 식별자 검증이 된다. 서버(외부 주소) 경유와 이 PC(내부
주소) 직접, 두 경로에서 같은 결과를 얻었다.

식별자:

| 대상 | 실측 |
|---|---|
| `F_GET_DELIVERY_DATE` | 인자 **2개** (`P_DATE`, `P_ORG`) |
| `ID_ITEM.MANUFACTURE_LEADTIME` | NUMBER |
| `IM_ITEM_PURCHASE_ORDER.ORDER_GROUP_NO` | VARCHAR2 |
| `IM_ITEM_PURCHASE_ORDER.MFS` | VARCHAR2 |
| `SEQ_PURCHASE_ORDER_NO` · `SEQ_ORDER_NO` | SEQUENCE |

문장 parse — **14개 전부 OK**:

- 477: 기준계획 집계 → `_S` · 재삽입(시퀀스) · BOM 전개 → TEMP · 소요량표 재작성
  (`F_GET_MAX_SUPPLIER_BY_ITEM`) · 기준계획 등록 · 재고 풀 초기화 · 안전재고 채우기
- 478: 소요량 집계 · 발주잔량 집계 · 도착분 집계 · **재고 집계 5가지 UNION 전부**
  (공정재고는 `ID_ITEM` 조인으로 거래유형을 가져오는 수정본) · 발주계획 생성
  (`ORDER_RATE`·`PAYMENT_TYPE`) · 발주속성 조회 · 단가 붙이기
- 리드타임 UPDATE · 작업일 보정 UPDATE · 발주 확정 INSERT · 발주그룹 채번 ·
  확정 표시 UPDATE · 올림 잉여 되돌리기 UPDATE

코드 검증: 프론트·백엔드 `tsc --noEmit` 통과.

## 미완료

- **원장에 실제로 써 보지는 않았다.** 477 전개·재고표시, 478 생성·단가 재설정·발주
  확정 모두 `parse` 까지만 확인했다. 발주 계열 표는 전부 0행이라(2020년 구축 이후
  미사용) 현장에서 한 번 돌려 봐야 한다.
- 설계 질문(순소요 vs 순발주)은 닫혔다. 계산식은 바꾸지 않는다.
